# 天气 API 与游戏天气 Mod 开发指南

状态：设计文档，尚未在 Ez2Lazer 中实现天气数据服务、天气 Mod 或着色器接入。本文约定后续开发路线和边界，不代表已存在可调用的 Ez2Lazer 天气 API。

## 当前状态

天气着色器及 `WeatherEffectContainer` 位于 `ez2lazer-framework`，目前尚未在 Ez2Lazer 中使用。框架组件只对调用方提供的子树绘制视觉效果；它不请求天气数据、不选择或调度天气、不保存用户设置，也不实现玩法判定。Ez2Lazer 需要自行决定何时启用效果、包裹哪个场景子树，并显式设置玩法范围。框架说明见本地相邻仓库的 [`weather-effects.md`](../../ez2lazer-framework/docs/weather-effects.md)。

框架目前提供 `DesertHeat`、`Underwater`、`OvercastRain`、`UnderwaterLightCurtain` 等效果，以及 `Intensity`、`AnimationSpeed`、`PreviewTime`、`Scope` 等参数。它们是渲染效果，不是气象类别；例如水下效果不应自动解释为当地天气。接入时应确认所用 framework 版本的接口与参数范围，并在 update 线程修改容器属性。

## 目标与边界

后续实现应把外部天气预报转换为稳定、与供应商无关的 Ez2Lazer 天气模型，再由 Ez2Lazer 决定如何展示或交给 Mod 使用。天气供应商、地理编码方式和地区覆盖范围尚未选定；更换供应商不应要求改动游戏界面、Mod 或着色器。

天气接入默认用于非竞技展示。网络不可用、定位未配置、数据过期或供应商失败时，游戏仍应正常运行，并退回缓存数据、手动天气或无天气效果。天气服务不得阻塞绘制或判定线程，也不应成为启动、选歌或开始游玩的必要条件。

## 建议架构

```text
用户选择地点 / 手动输入坐标
            ↓
Ez2Lazer 天气服务 ──→ 供应商适配器 ──→ 外部天气预报 API
            ↓              规范化、校验
规范化天气快照 + 缓存 + 数据新鲜度
            ├──→ 天气展示 / 天气视觉 Mod ──→ WeatherEffectContainer
            └──→ （可选）游玩开始时固定的天气 Mod 状态
```

天气数据、供应商适配器、用户设置、展示和 Mod 逻辑属于 Ez2Lazer。Framework 只保留通用渲染能力，不应依赖具体天气服务商、用户位置、Ez2Lazer 设置或成绩规则。

建议的内部服务契约如下，仅为接口草图：

```csharp
Task<WeatherResult> GetForecastAsync(
    WeatherRequest request,
    CancellationToken cancellationToken);
```

`WeatherRequest` 表达用户选定的位置和所需时间范围；供应商适配器负责调用外部服务并把响应转换为规范模型。界面与 Mod 只依赖天气服务，不直接拼接供应商 URL 或解析供应商 JSON。具体类型、命名空间、依赖注入位置应在实现时遵循 Ez2Lazer 现有服务结构后再确定。

建议的规范化天气快照字段：

| 字段 | 约定 |
|------|------|
| `Condition` | 统一天气枚举：晴、云、雾、雨、雪、雷暴、未知；必须保留 `Unknown` 以兼容供应商新增代码 |
| `TemperatureC` | 摄氏温度，可空；内部统一单位，显示时再按用户偏好换算 |
| `PrecipitationMmPerHour` | 降水强度，可空，毫米/小时 |
| `WindSpeedMetersPerSecond` | 风速，可空，米/秒 |
| `WindDirectionDegrees` | 风向，可空，0–359 度 |
| `CloudCoverPercent` | 云量，可空，0–100 |
| `FetchedAtUtc` | 客户端取得数据的 UTC 时间，用于新鲜度判断 |
| `ValidAtUtc` | 预报对应的 UTC 时间；当前实况和未来预报必须可区分 |
| `SourceId` / `Attribution` | 供应商标识及按其条款要求展示的来源信息 |

规范模型使用明确单位和 UTC 时间；供应商原始天气代码只留在适配器边界，不让 UI 或 Mod 依赖它。缺失或无效的数值字段应变为空值，不能用 0 伪装成真实观测。

## 地点、供应商和隐私

- 首版优先采用用户主动选择的城市或手动位置。若未来提供设备定位，必须由用户显式启用，并可随时关闭；不得静默读取精确位置。
- 不使用 IP 地址推断位置作为默认行为。坐标不写入日志、崩溃信息、成绩或回放；如需保存地点，应在用户确认后采用最小必要数据。
- 选供应商前核实目标地区的实况/预报覆盖、更新频率、配额、速率限制、商业/非商业许可、署名要求、数据保存限制及客户端密钥规则。供应商可以是公开预报服务、地区官方服务或需要密钥的商业服务，具体选择待后续确认。
- 需要保密的 API 密钥不能硬编码或随桌面客户端发布。若供应商要求保密密钥，应评估受控代理服务或更换服务商；不要把客户端混淆当作密钥保护。
- 对供应商数据遵循其使用条款和署名要求。发布前重新核对条款与配额，不把当前免费或无需密钥的状态视为永久保证。

## 请求、缓存与错误处理

- 仅在用户启用天气功能后请求。使用异步 HTTP 调用、取消令牌和有限超时；不要在 update/draw、音频或判定线程等待网络。
- 为实况和预报分别定义缓存有效期，并尊重供应商更新频率、配额、`Retry-After` 和服务条款。缓存先从进程内方案开始；持久缓存需单独确定保留时长、位置隐私和清理策略。
- 对可重试的只读请求使用有限次数的退避重试；避免高频轮询。解析时检查 HTTP 状态、响应大小、必需字段、时间戳、单位换算和数值有限性。
- 返回明确的数据状态，例如 `Fresh`、`Cached`、`Unavailable`。网络失败时优先使用仍可接受的缓存并标明数据时间；没有可用数据时返回 `Unavailable`，由调用方关闭天气效果或使用用户选择的手动天气。
- 错误日志记录供应商、错误类别和请求时间即可，不记录坐标、完整 URL 中的敏感参数、密钥或未经筛选的响应正文。

## 天气效果映射

天气服务输出气象事实；独立的展示映射负责将其转换为效果与参数。不得让天气供应商直接决定 framework 枚举或着色器参数。建议采用可配置映射，未配置或不支持的条件返回 `None`：

| 天气输入 | 映射建议 |
|----------|----------|
| 雨、阴、较高云量 | 可选择 `OvercastRain`，并将降水/风力映射到经过验证的效果参数范围 |
| 高温、干燥 | 可选 `DesertHeat`；应由温度阈值和用户选项共同决定，不要仅凭“晴”触发 |
| 雪、雾、雷暴 | 当前效果集合没有明确的一一对应项，默认不启用效果 |
| `Underwater`、`UnderwaterLightCurtain` | 作为主题/趣味效果，由手动设置或游戏 Mod 选择，不映射为当地天气 |

展示层只把 `WeatherEffectContainer` 放在希望受影响的背景或场景子树周围。若需要保护音符、HUD、按钮或前景，应确保它们不在容器作用范围内。由 Ez2Lazer 的场景所有者设置 `Scope` 和 `IsGameplay`；天气数据更新后在正确线程切换 `Effect` 与参数。强度为零、效果为 `None` 或范围不匹配时应允许框架走直绘路径。

## 天气 Mod 与成绩一致性

建议先实现纯视觉 `WeatherVisualMod`：天气只改变背景观感，不影响判定、分数、血量、谱面或成绩排名。允许来源包括当地预报、手动选择、固定场景或带种子的随机天气；所有来源都应可关闭并有确定的无天气回退。

如果未来设计会改变玩法的 `WeatherGameplayMod`，必须在游玩开始前解析并固定天气状态；游玩中不刷新当地天气、不发起天气请求。游玩过程只能读取这个固定状态，以确保结果可复现。回放需要包含足以还原玩法的天气类型、参数与随机种子，不能包含经纬度或 API 凭据。任何天气对成绩/回放数据格式的影响都应另行评审，并在确认具体方案后实现；当前文档不要求改动成绩 schema。

## 推荐实施顺序

1. 确定首个目标平台、目标地区、供应商、数据许可及用户地点设置方式。
2. 在 Ez2Lazer 实现供应商无关的天气模型、适配器、缓存/新鲜度状态和离线回退；先验证手动地点与网络错误场景。
3. 单独增加 opt-in 的菜单或背景视觉入口，接入 framework 天气容器，并提供关闭、强度和效果选择。
4. 若仍需要玩法 Mod，再单独确定是否纯视觉、游玩开始时如何冻结状态，以及回放/成绩兼容方案；确认后再实现。

本指南是未来设计入口。开始代码实现前，应先按仓库协作约定提交具体实现路线供确认；本指南不会授权修改 framework、增加成绩 schema 或接入某个特定天气供应商。
