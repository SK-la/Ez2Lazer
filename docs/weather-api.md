# 天气 API 与游戏天气 Mod 开发指南

状态：Framework 天气视觉效果已接入主界面背景、选歌背景和 Playfield。天气数据服务与天气 Mod 尚未实现。

## 当前状态

天气着色器及 `WeatherEffectContainer` 位于 `ez2lazer-framework`。Ez2Lazer 目前提供背景与 Playfield 的手动视觉效果入口。框架组件只对调用方提供的子树绘制视觉效果；它不请求天气数据、不选择或调度天气、不保存用户设置，也不实现玩法判定。Ez2Lazer
决定何时启用效果、包裹哪个场景子树，并显式设置玩法范围。框架说明见本地相邻仓库的 [
`weather-effects.md`](../../ez2lazer-framework/docs/weather-effects.md)。

背景效果默认关闭，可在主菜单设置中选择效果和强度；关闭“主界面使用天气效果”后，选歌背景仍可应用效果。Playfield 使用独立的效果和强度设置，默认关闭，只影响 `DrawableRuleset` 子树。所有入口均为手动视觉效果，不会读取天气预报或影响判定、分数与回放。

框架目前提供 `DesertHeat`、`Underwater`、`OvercastRain`、`UnderwaterLightCurtain` 等效果，以及 `Intensity`、`AnimationSpeed`、
`PreviewTime`、`Scope` 等参数。它们是渲染效果，不是气象类别；例如水下效果不应自动解释为当地天气。接入时应确认所用 framework
版本的接口与参数范围，并在 update 线程修改容器属性。

## 目标与边界

后续实现应把外部天气预报转换为稳定、与供应商无关的 Ez2Lazer 天气模型，再由 Ez2Lazer 决定如何展示或交给 Mod
使用。天气供应商、地理编码方式和地区覆盖范围尚未选定；更换供应商不应要求改动游戏界面、Mod 或着色器。

天气接入默认用于非竞技展示。网络不可用、定位未配置、数据过期或供应商失败时，游戏仍应正常运行，并退回缓存数据、手动天气或无天气效果。天气服务不得阻塞绘制或判定线程，也不应成为启动、选歌或开始游玩的必要条件。

## 建议架构

```text
用户选择地点 / 手动输入坐标
            ↓
Ez2Lazer 天气服务 ──→ 供应商适配器 ──→ 外部天气预报 API
            ↓              规范化、校验
规范化天气快照 + 缓存 + 数据新鲜度
            ├──→ 天气展示 / 天气视觉 Mod ──→ WeatherEffectContainer
            └──→ （可选）游玩开始时固定的天气 Mod 状态
```

天气数据、供应商适配器、用户设置、展示和 Mod 逻辑属于 Ez2Lazer。Framework 只保留通用渲染能力，不应依赖具体天气服务商、用户位置、Ez2Lazer
设置或成绩规则。

建议的内部服务契约如下，仅为接口草图：

```csharp
Task<WeatherResult> GetForecastAsync(
    WeatherRequest request,
    CancellationToken cancellationToken);
```

`WeatherRequest` 表达用户选定的位置和所需时间范围；供应商适配器负责调用外部服务并把响应转换为规范模型。界面与 Mod
只依赖天气服务，不直接拼接供应商 URL 或解析供应商 JSON。具体类型、命名空间、依赖注入位置应在实现时遵循 Ez2Lazer 现有服务结构后再确定。

建议的规范化天气快照字段：

| 字段                       | 约定                                                                                  |
|----------------------------|---------------------------------------------------------------------------------------|
| `Condition`                | 统一天气枚举：晴、云、雾、雨、雪、雷暴、未知；必须保留 `Unknown` 以兼容供应商新增代码 |
| `TemperatureC`             | 摄氏温度，可空；内部统一单位，显示时再按用户偏好换算                                  |
| `PrecipitationMmPerHour`   | 降水强度，可空，毫米/小时                                                             |
| `WindSpeedMetersPerSecond` | 风速，可空，米/秒                                                                     |
| `WindDirectionDegrees`     | 风向，可空，0–359 度                                                                  |
| `CloudCoverPercent`        | 云量，可空，0–100                                                                     |
| `FetchedAtUtc`             | 客户端取得数据的 UTC 时间，用于新鲜度判断                                             |
| `ValidAtUtc`               | 预报对应的 UTC 时间；当前实况和未来预报必须可区分                                     |
| `SourceId` / `Attribution` | 供应商标识及按其条款要求展示的来源信息                                                |

规范模型使用明确单位和 UTC 时间；供应商原始天气代码只留在适配器边界，不让 UI 或 Mod 依赖它。缺失或无效的数值字段应变为空值，不能用
0 伪装成真实观测。

## 地点、供应商和隐私

- 首版优先采用用户主动选择的城市或手动位置。若未来提供设备定位，必须由用户显式启用，并可随时关闭；不得静默读取精确位置。
- 不使用 IP 地址推断位置作为默认行为。坐标不写入日志、崩溃信息、成绩或回放；如需保存地点，应在用户确认后采用最小必要数据。
- 选供应商前核实目标地区的实况/预报覆盖、更新频率、配额、速率限制、商业/非商业许可、署名要求、数据保存限制及客户端密钥规则。供应商可以是公开预报服务、地区官方服务或需要密钥的商业服务，具体选择待后续确认。
- 需要保密的 API 密钥不能硬编码或随桌面客户端发布。若供应商要求保密密钥，应评估受控代理服务或更换服务商；不要把客户端混淆当作密钥保护。
- 对供应商数据遵循其使用条款和署名要求。发布前重新核对条款与配额，不把当前免费或无需密钥的状态视为永久保证。

## 请求、缓存与错误处理

- 仅在用户启用天气功能后请求。使用异步 HTTP 调用、取消令牌和有限超时；不要在 update/draw、音频或判定线程等待网络。
- 为实况和预报分别定义缓存有效期，并尊重供应商更新频率、配额、`Retry-After` 和服务条款。缓存先从进程内方案开始；持久缓存需单独确定保留时长、位置隐私和清理策略。
- 对可重试的只读请求使用有限次数的退避重试；避免高频轮询。解析时检查 HTTP 状态、响应大小、必需字段、时间戳、单位换算和数值有限性。
- 返回明确的数据状态，例如 `Fresh`、`Cached`、`Unavailable`。网络失败时优先使用仍可接受的缓存并标明数据时间；没有可用数据时返回
  `Unavailable`，由调用方关闭天气效果或使用用户选择的手动天气。
- 错误日志记录供应商、错误类别和请求时间即可，不记录坐标、完整 URL 中的敏感参数、密钥或未经筛选的响应正文。

## 天气效果映射

天气服务输出气象事实；独立的展示映射负责将其转换为效果与参数。不得让天气供应商直接决定 framework
枚举或着色器参数。建议采用可配置映射，未配置或不支持的条件返回 `None`：

| 天气输入                               | 映射建议                                                            |
|----------------------------------------|---------------------------------------------------------------------|
| 雨、阴、较高云量                       | 可选择 `OvercastRain`，并将降水/风力映射到经过验证的效果参数范围    |
| 高温、干燥                             | 可选 `DesertHeat`；应由温度阈值和用户选项共同决定，不要仅凭“晴”触发 |
| 雪、雾、雷暴                           | 当前效果集合没有明确的一一对应项，默认不启用效果                    |
| `Underwater`、`UnderwaterLightCurtain` | 作为主题/趣味效果，由手动设置或游戏 Mod 选择，不映射为当地天气      |

展示层只把 `WeatherEffectContainer` 放在希望受影响的背景或场景子树周围。若需要保护音符、HUD、按钮或前景，应确保它们不在容器作用范围内。由
Ez2Lazer 的场景所有者设置 `Scope` 和 `IsGameplay`；天气数据更新后在正确线程切换 `Effect` 与参数。强度为零、效果为 `None`
或范围不匹配时应允许框架走直绘路径。

## 使用场景设计

天气效果分为背景层天气和游玩层天气两类。两类可以读取同一份规范化天气快照与效果映射，但由各自的场景实例控制作用范围，避免效果跨界面泄漏。天气服务返回
`Fresh`、`Cached` 或 `Unavailable` 状态；无可用天气时，背景层可关闭效果或使用手动选择，游玩层沿用已固定的状态或不启用天气。

### 背景层天气：主界面与选歌界面

选歌界面的背景可能由多个背景 Drawable 或背景组件组成，例如谱面背景、场景底图和动态背景叠层。应先把它们作为一个完整的背景层组合，再整体放进一个
`WeatherEffectContainer`。天气效果由此作用于整组背景内容；选歌控件、工具栏和其他前景仍作为容器外的同级内容绘制。

主界面使用独立的 `WeatherEffectContainer`，只包裹主界面背景层。提供实例级开关 `EnableMainMenuWeather`
，界面文案可为“主界面使用天气效果”。天气总开关开启且 `EnableMainMenuWeather`
关闭时，天气只作用于选歌背景；开启该开关时，天气同时作用于主界面和选歌背景。天气总开关关闭时，两处均不应用天气。

使用示例：用户选择城市并启用天气，天气快照映射为 `OvercastRain`。选歌界面将其所有背景内容作为整体呈现阴雨效果。若用户关闭
`EnableMainMenuWeather`，主界面背景保持原样，选歌界面的天气效果继续生效。`Underwater` 等主题效果由手动选择或游戏 Mod
启用，不根据当地降雨自动推导。

```text
主界面
├── 天气容器（EnableMainMenuWeather 控制）
│   └── 主界面背景层
└── 主界面 UI 前景

选歌界面
├── 天气容器（选歌背景天气启用时）
│   └── 背景内容 A + 背景内容 B + 其他背景内容
└── 选歌控件与其他 UI 前景
```

这里的“全局背景”指天气体验可用于多个界面的背景层，不代表将容器放在应用最外层并影响所有
UI。主界面和选歌界面的容器应独立，以便单独关闭主界面效果而保留选歌背景效果。若场景过渡会同时显示两个界面，应避免同一背景被两个容器重复着色。

### 游玩层天气：只影响 Playfield

游玩时，`WeatherEffectContainer` 只包住实际 Playfield 绘制内容。HUD、暂停界面、成绩提示及其他 UI 位于容器外。场景所有者应明确设置容器的
Gameplay 范围与 `IsGameplay`，确保菜单背景配置不会误用于游玩场景。

```text
游玩界面
├── Playfield 天气容器（Gameplay 范围）
│   └── Playfield 绘制内容
└── HUD、暂停界面与其他 UI
```

纯视觉游玩天气改变 Playfield 的呈现，例如雨幕、阴天色调或热浪，不改变命中判定、分数、血量或谱面。接入时需逐个效果检查音符、判定线与关键提示的可读性，并提供关闭或降低强度的选项。

若天气还要改变实际玩法规则，则由独立的 `WeatherGameplayMod` 表达规则变化，天气容器仍只承担 Playfield
的视觉效果。开始游玩前解析并固定天气类型、参数和随机种子，整局及回放均使用同一份状态；游玩中不刷新当地天气、不发起天气请求。回放需要包含足以还原玩法的天气状态，不包含经纬度或
API 凭据。对成绩或回放数据格式的影响另行评审。

## 天气 Mod 与成绩一致性

当前纯视觉天气入口分别支持背景层与 Playfield
层；两者只改变对应场景的观感，不影响判定、分数、血量、谱面或成绩排名。天气可来自当地预报、手动选择、固定场景或带种子的随机选择；所有来源都应可关闭并有确定的无天气回退。

若实现 `WeatherGameplayMod`
，它必须与上述视觉天气入口分开，并在游玩开始前解析、固定天气状态；游玩中不刷新当地天气、不发起天气请求。游玩过程只能读取这个固定状态，以确保结果可复现。回放需要包含足以还原玩法的天气类型、参数与随机种子，不能包含经纬度或
API 凭据。任何天气对成绩或回放数据格式的影响都应另行评审，并在确认具体方案后实现；当前文档不要求改动成绩 schema。

## 推荐实施顺序

1. 确定首个目标平台、目标地区、供应商、数据许可及用户地点设置方式。
2. 在 Ez2Lazer 实现供应商无关的天气模型、适配器、缓存/新鲜度状态和离线回退；先验证手动地点与网络错误场景。
3. 菜单背景和 Playfield 的手动视觉入口已接入，后续可在确定天气供应商后连接天气快照与效果映射。
4. 若仍需要玩法 Mod，再单独确定游玩开始时如何固定状态，以及回放/成绩兼容方案；确认后再实现。

本指南不会授权修改 framework、增加成绩 schema 或接入某个特定天气供应商。
